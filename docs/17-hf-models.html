この章でつくるもの

第4部まで、あなたは「LLMを作る側」でした。ここからは、世界中の研究機関や企業が公開している事前学習済みモデルを借りて、自分の目的に合わせて鍛える側に回ります。この章ではその準備として、Hugging Faceでのモデルの選び方、ベースモデルとチャットモデルの違い、プロンプトの工夫とその限界を、実験しながら学びます。

これまでの復習とつながり：第1章〜第3章・第15章とのつながり

  • 第1章：pipeline で手軽にチャットを動かし、会話は role（system / user / assistant）の台本形式（apply_chat_template）で渡されることを見ました。
  • 第2章・第3章：特殊トークン（<|im_end|>）・コンテキスト長の上限・temperature や do_sample といった生成設定（generation_config）の中身を学びました。
  • 第15章：大きな事前学習は「借りる」のが正解であり、学習には1パラメータ約16バイトのVRAMが必要になることを見積もりました。

この章では、その知識を土台にして、モデルを借りる前のチェック項目（ライセンス・ベース vs チャット・履歴管理・プロンプトの限界・推論 vs 学習のVRAM）を実務レベルで整理します。

理論の小部屋：ライセンスは必ず読む

モデルにも、ソフトウェアと同じようにライセンス（利用条件）があります。

  • Apache 2.0 / MIT：商用利用も改変も自由（Qwen2.5の多くのサイズ、など）
  • 独自ライセンス：Llama（Meta）やGemma（Google）は、独自の利用規約に同意する必要がある。条件付きで商用利用可

学校の課題や個人の勉強ならほとんど問題ありませんが、作ったものを公開したり、アルバイト先や就職先で使ったりするときには、必ず確認しましょう。学習に使ったデータセットのライセンスも同様です。

ベースモデルとチャットモデル

コツ：実行環境とリソースの目安（CPUでも実行可能）

  • 環境：無料GPU（Colab T4）推奨ですが、0.5BモデルのためCPUでも実行できます。
  • ダウンロードとメモリ：ベースモデルとチャットモデルの2つを合わせて初回約2GBをダウンロードします。必要メモリはGPU（float16）でVRAM約2〜3GB、CPU（float32）でRAM約4〜5GBです。
  • 所要時間と代替手順：GPUなら各生成は数秒、CPUでは1回あたり十数秒〜数十秒（レビュー6問×2通りは数分）かかります。GPUが借りられない日やRAMが厳しいときは、ベースモデルの実験が終わった後に del base してからチャットモデルを読み込むと軽く動かせます。
  • ライブラリ互換性：dtype= 引数は transformers >= 4.56（5系含む）に対応しています（古い版では torch_dtype= に読み替えてください）。また device_map="auto" には accelerate パッケージが必要です（Colabには標準導入済み。ローカル環境はリポジトリの requirements-book.txt を参照）。

Qwen2.5-0.5Bには、2つの版があります。Qwen2.5-0.5B（ベースモデル）と、Qwen2.5-0.5B-Instruct（チャットモデル、指示に従うモデル）です。同じ質問をして、違いを見てみましょう。GPUのランタイムで実行してください。

Python（Colabのセルに貼って実行）
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

gpu = torch.cuda.is_available()
dtype = torch.float16 if gpu else torch.float32

def load(name):
    tok = AutoTokenizer.from_pretrained(name)
    model = AutoModelForCausalLM.from_pretrained(name, dtype=dtype, device_map="auto")
    return tok, model

base_tok, base = load("Qwen/Qwen2.5-0.5B")
chat_tok, chat = load("Qwen/Qwen2.5-0.5B-Instruct")
print("読み込み完了")
出力
読み込み完了

Pythonの道具箱：AutoModelForCausalLM って何？

AutoModel ではなく AutoModelForCausalLM という長い名前を使うのはなぜでしょう？ AutoModel はTransformerの胴体部分（各トークンの特徴量ベクトルを出すところまで）しか読み込みません。一方、AutoModelForCausalLM（Causal Language Model：因果的言語モデル）は、その上に第12章や第15章で作った「次のトークンを予測する出力層（lm_head）」をちゃんと乗せたモデルを読み込んでくれます。文章の続きを生成したいときは、必ずこの ForCausalLM のほうを使います。

ベースモデルに、質問の文章をそのまま渡してみます。

Python（Colabのセルに貼って実行）
def complete(tok, model, text, n=60):
    inputs = tok(text, return_tensors="pt").to(model.device)
    out = model.generate(**inputs, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

print(complete(base_tok, base, "日本で一番高い山は何ですか？"))

def ask(tok, model, messages, n=100):

                                     return_tensors="pt", return_dict=True).to(model.device)
    out = model.generate(**inputs, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

理論の小部屋：LLMができるまでの3段階

チャットモデルは、ふつう次の3段階で作られます。

  1. 事前学習（pre-training）：大量の文章で「次のトークン予測」を学ぶ（第13〜15章でやったこと）。ここでできるのがベースモデル。知識と文章力は身につくが、会話の作法は知らない
  2. SFT（教師ありファインチューニング）：「質問 → 良い答え」の例を数万〜数百万件、チャットテンプレート（第1章の台本形式）で学ばせる。会話の作法と、<|im_end|> で止まることを覚える（第18章）
  3. 好みの学習（RLHF・DPOなど）：同じ質問への2つの答えのどちらが良いかを人間が選び、良い方を出しやすくする。安全性や丁寧さもここで整える（第22章）

ベースモデルは「知識豊富だけど空気が読めない人」、チャットモデルは「それに接客研修を受けさせた人」、というイメージです。

理論の小部屋：「記憶」の正体

ChatGPTなどのアプリが会話を覚えているように見えるのは、アプリが過去の会話を毎回まとめてLLMに送っているからです。会話が長くなると、その分トークンが増え、計算が重くなり（第16章のKVキャッシュ）、やがてコンテキスト長（第2章）の上限に達します。長い会話で、最初のほうの話を忘れてしまうのはこのためです。

基礎の補足LLMはステートレス！複数ターン messages の仕組みと履歴の切り詰め

LLMの推論呼び出しは1回ごとに記憶がリセットされます（ステートレス）。アプリ側では毎ターン次のように messages リストを育てて送り直します。

Python（読むだけ・実行しなくてOK）
# 1ターン目：[system, user1] を送る → assistant1 を受け取って追加
# 2ターン目：[system, user1, assistant1, user2] を全部送る → assistant2 を追加
# 3ターン目：履歴が長すぎたら、`system` は先頭に絶対残しつつ、古い (user, assistant) から捨てる！
sys_msgs = [m for m in messages if m["role"] == "system"]
dialog   = [m for m in messages if m["role"] != "system"]
trimmed  = sys_msgs + dialog[-2 * max_turns:]   # 直近 max_turns 往復だけ保持

「system メッセージを保護しながら直近の往復だけ残す」のが、実務のチャットアプリでコンテキスト長オーバーを防ぐ基本パターンです。

プロンプトの工夫と、その限界

モデルの重みを変えずに、入力の書き方（プロンプト）だけで性能を上げる工夫を、プロンプトエンジニアリングと呼びます。小さな実験で効果を確かめてみましょう。お題は「レビューが肯定的か否定的かを判定する」です。

Python（Colabのセルに貼って実行）
reviews = [
    ("このラーメン、スープが最高においしかった！", "肯定"),
    ("店員さんの態度が悪くて二度と行かない。", "否定"),
    ("値段のわりに量が少なくてがっかり。", "否定"),
    ("駅から近くて便利、また来たいです。", "肯定"),
    ("注文してから40分も待たされた。", "否定"),
    ("期待していなかったけど、意外とよかった。", "肯定"),
]

def classify(review, few_shot=False):
    msgs = [{"role": "system", "content": "レビューが肯定的なら「肯定」、否定的なら「否定」とだけ答えてください。"}]
    if few_shot:   # 例を2つ見せる
        msgs += [{"role": "user", "content": "最高の一日でした。"}, {"role": "assistant", "content": "肯定"},
                 {"role": "user", "content": "最悪の対応でした。"}, {"role": "assistant", "content": "否定"}]
    msgs.append({"role": "user", "content": review})
    return ask(chat_tok, chat, msgs, n=5).strip()

for few in [False, True]:
    correct = sum(classify(r, few) == label for r, label in reviews)
    print(("few-shot " if few else "zero-shot"), f"正解 {correct}/{len(reviews)}")
出力の例（数値や文章は実行ごとに変わってOK）
zero-shot 正解 4/6
few-shot  正解 6/6

理論の小部屋：プロンプト技法

  • zero-shot：お手本なしで、指示だけを与える
  • few-shot：答え方のお手本（例）を数個見せてから聞く。小さなモデルほど、出力の形式がそろって効果が大きい
  • 段階的に考えさせる（Chain-of-Thought）：「ステップごとに考えてから答えてください」と頼むと、計算や推論の問題で正答率が上がることがある。答えの前に考える過程を書かせることで、その過程が次のトークンの手がかりになるため（第1章：LLMは自分の出力を読みながら次を予測する）
  • 役割（system）：第1章のボンゴ先生のように、立場や口調を指定する

あなたの結果はどうでしたか？ 上の出力は一例で、モデルの版などによって、正解数は変わります。few-shotのほうが良くなることが多いですが、同じだったり、逆になったりすることもあります。

ただし、プロンプトには限界があります。どちらの結果が出たとしても、6問は少なすぎて、偶然の差かもしれません。本当に効果があるかを確かめるには、もっと多くの問題と、統計の考え方が必要です（第20章）。また、小さなモデルに知らない知識はプロンプトでは教えられませんし、毎回お手本を入れるとトークン（お金と時間）を食います。そこで、モデル自体を鍛える ファインチューニング（第18〜19章）や、資料を検索して渡す RAG（第21章）の出番になります。

基礎の補足使い分けの地図：few-shotプロンプト vs ファインチューニング（第18〜19章） vs RAG（第21章）
手法 重みを変える？ 得意なこと 限界・注意点
プロンプト（zero/few-shot） 変えない すぐ試せる・出力形式を軽く整える 毎回お手本分のトークンを消費／未知の専門知識は教えきれない／少問題では偶然に左右される
ファインチューニング（SFT / LoRA） 変える（第18〜19章） 独自の口調・専門フォーマット・特定タスクの精度を定着させ、入力トークンも節約できる 良質な学習データとGPU計算が必要／最新事実の更新には不向き
RAG（検索拡張生成） 変えない（第21章） 社内資料や毎日変わる最新情報を根拠つきで参照する 検索精度が低いと誤った資料を渡してしまう

やってみよう：段階的に考えさせる

ask(chat_tok, chat, [{"role": "user", "content": "りんごが3個入った箱が4箱あり、2個食べました。残りは何個？"}]) と、同じ質問の最後に「ステップごとに考えてから答えてください。」を付けたものを比べてみましょう。小さなモデルなので、どちらも間違えるかもしれません。それも大事な観察結果です。

モデルの大きさとGPUメモリ

借りるモデルを選ぶとき、一番の制約はGPUのメモリです。推論（使うだけ） に必要なメモリは、だいたい「パラメータ数 × 1個のバイト数」です。

Python（Colabのセルに貼って実行）
def infer_gb(n_params_billion, bytes_per_param):
    return n_params_billion * bytes_per_param

print("        float16   8ビット   4ビット")
for size in [0.5, 1.5, 3, 7, 14]:
    print(f"{size:4}B  {infer_gb(size, 2):6.2f}GB {infer_gb(size, 1):6.2f}GB {infer_gb(size, 0.5):6.2f}GB")
出力
        float16   8ビット   4ビット
 0.5B    1.00GB   0.50GB   0.25GB
 1.5B    3.00GB   1.50GB   0.75GB
   3B    6.00GB   3.00GB   1.50GB
   7B   14.00GB   7.00GB   3.50GB
  14B   28.00GB  14.00GB   7.00GB

T4（約15GB）なら、float16で3B程度まで余裕を持って動かせます。7Bはfloat16だとギリギリ（実際には計算用のメモリも必要なので厳しい）ですが、4ビットに量子化すれば3.5GBで動きます。量子化は第19章で学びます。

理論の小部屋：safetensors

モデルの重みのファイルには model.safetensors という形式がよく使われます。昔よく使われていた pytorch_model.bin（Pythonの pickle 形式）は、読み込むときに任意のプログラムが実行される危険がありました。知らない人が公開したファイルを開いたら、ウイルスが動く、ということが理論上ありえたのです。safetensors は数の並びだけを保存する形式なので、そうした危険がありません。知らない人のモデルを使うときは、safetensors形式を選びましょう。

基礎の補足推論VRAM vs 学習VRAM：同じモデルでも必要メモリが「約8倍」違う！

第15章の学習メモリ見積もり（混合精度＋AdamW＝1パラメータ約16バイト）と、この章の推論メモリ見積もりを並べて見比べてみましょう。

モデル規模 推論（4ビット：0.5B/param） 推論（float16：2B/param） 全パラメータ学習（AdamW：16B/param） T4（15GB）での可否
0.5B 0.25 GB 1.0 GB 8.0 GB（＋活性化） 推論も全学習もOK（第18章）
3B 1.5 GB 6.0 GB 48.0 GB（＋活性化） float16推論は余裕、全学習は不可
7B 3.5 GB 14.0 GB 112.0 GB（＋活性化） 4ビット推論やQLoRA（第19章）ならOK！

推論では重み（＋KVキャッシュ）だけで済むのに対し、全パラメータ学習では fp16重み・fp32控え・勾配・AdamWの2つの状態・活性化を全部載せるため、約8倍以上のVRAMが必要です。

Hugging Faceのアカウントとトークン

第18章以降で、自分で鍛えたモデルをHugging Faceに保存したり、利用規約への同意が必要なモデルを使ったりするには、アカウントとアクセストークンが必要です。

  1. https://huggingface.co/join で無料アカウントを作る（メールアドレスの確認まで）
  2. 右上のアイコン →「Settings」→「Access Tokens」→「Create new token」
  3. 種類（Token type）は、最初は Read（読み取り専用）を選ぶ。モデルをアップロードするときだけ Write の権限があるものを作る
  4. 表示されたトークン（hf_ で始まる文字列）をコピー

つまずき注意：トークンは「家の鍵」

アクセストークンは、あなたのアカウントの鍵です。ノートブックのコードに直接書いてはいけません。ノートブックを人に見せたり、GitHubに上げたりしたときに、鍵ごと渡してしまうからです。Colabでは、左側の 鍵のアイコン（シークレット） に HF_TOKEN という名前で保存し、「ノートブックからのアクセス」をオンにします。すると、コードに書かなくても、自動で使われるようになります（第1章で出た黄色い警告が消えます）。もし漏らしてしまったら、すぐにHugging Faceの設定画面でそのトークンを削除（Invalidate）しましょう。

コードからトークンを使う必要があるときは、次のように取り出します（シークレットが設定されていないとエラーになります）。

Python（Hugging Faceにつないで実行）
from google.colab import userdata
from huggingface_hub import login
login(token=userdata.get("HF_TOKEN"))

0円のコツ：無料でできること

Hugging Faceの無料アカウントで、公開モデル・データセットのダウンロード、自分のモデル・データセットの公開（公開リポジトリ）ができます。アプリを公開する「Spaces」は、無料アカウントだと使える種類が限られます（2026年10月時点の公式ドキュメントでは、CPUで動くGradioアプリの新規作成には有料プランが必要で、無料では「ZeroGPU」のSpaceが2つまで、または静的ページのSpaceが使えます）。第24章では、0円で確実に公開できる方法を紹介します。

つまずき注意：よくあるつまずき

  • OSError: … is not a local folder and is not a valid model identifier：モデル名のつづりが違うか、利用規約への同意が必要なモデル（gated model）です。Hugging Faceのモデルページで「Agree and access」を押し、HF_TOKEN を設定しましょう。
  • CUDA out of memory：モデルを2つ同時に読み込んでいるとメモリを食います。使わなくなったモデルは del base で消し、torch.cuda.empty_cache() を実行しましょう。
  • ベースモデルが同じ文をくり返す：正常です（この章の実験のとおり）。会話させたいならチャットモデル（Instruct）を使いましょう。
  • The following generation flags are not valid and may be ignored: ['temperature', 'top_p', 'top_k'] という英語の表示：エラーではなく、ただのお知らせです。do_sample=False（サイコロを振らない）にしたので、モデル付属の設定にある温度などが使われない、と言っているだけです。無視してOKです。

できたらチェック

まとめ

  • チャットモデルは、事前学習 → SFT（第18章）→ 好みの学習（第22章） の3段階で作られる。ベースモデルは「続きを書く」だけ
