この章でつくるもの

第2章で、Qwenのトークナイザーが「よく出るバイトの並びを1トークンにまとめている」ことを見ました。この章では、その仕組み BPE（Byte Pair Encoding）を自分で実装します。アルゴリズムは驚くほど単純で、「いちばんよく出る隣どうしのペアを合体させる」を何百回もくり返すだけ。最後に、Hugging Faceの高速な実装と比べて、自作GPTをBPEで学習させてみます。

これまでの復習とつながり：第2章とのつながり

  • 第2章：テキストはUTF-8の バイト列（0〜255の整数） で表せ、日本語1文字はおおよそ3バイトになることを見ました。また、QwenのバイトレベルBPEでは「鰯」のような珍しい漢字が3バイトの断片に分かれても未知語にならず完全に復元できました。
  • 第12〜13章：これまでの自作GPTは「1文字＝1トークン」で動かしてきましたが、文章が長くなりやすいという限界がありました。

この章では、その2つをつなぎ、0〜255のバイト列から出発して「よく出るペアを合体させる」バイトレベルBPEをゼロから自作します。

ミナト

第2章で見た「鰯」が3バイトのまま残っていた理由が、ついに分かるんですね。

ボンゴ先生

そう。BPEは、もともと1994年に「データ圧縮」の方法として考えられた。ZIPファイルの親戚だね。それが20年以上たって、LLMの入り口になった。研究の世界では、昔の小さなアイデアが、思わぬところで主役になることがよくある。キミの基本情報の勉強も、いつか思わぬところで主役になるかもしれないよ。

まずは手で体験

下のデモで、「1回合体」を何回か押してみてください。BPEのすべてがここにあります。

  1. 隣り合う2つのトークンの組を全部数える
  2. いちばん多い組を、新しい1つのトークンに合体させる（この「合体ルール」を覚えておく）
  3. 1に戻る

これだけです。合体のたびにトークン数が減り（文章が短くなり）、語彙の種類が増えます。

準備：文章をバイトにする

コツ：実行環境とリソースの目安

  • 環境：CPUで完走できます（GPU不要）。
  • ダウンロードとメモリ：初回に青空文庫『こころ』（約350KB）と教材コード minigpt.py（約4KB）を取得します。必要RAMは約1GBです。
  • 所要時間：自作BPEの300マージはCPUで1〜2分、tokenizers 版は数秒、章末のBPE版ミニGPT学習（1500ステップ）はCPUで3〜6分（GPUなら十数秒）です。時間を短縮したいときは range(1501) を range(501) にしても傾向を確認できます。
  • ライブラリ：推奨バージョンはリポジトリの requirements-book.txt を参照してください。

本物のBPEは、文字ではなく UTF-8のバイト（0〜255の数）から始めます（第2章）。こうすると、どんな文字でも最初から表せるので、「辞書にない文字」が存在しなくなります。

ステップ1：ペアを数える

Python（Colabのセルに貼って実行）
def get_stats(ids):
    counts = {}
    for pair in zip(ids, ids[1:]):
        counts[pair] = counts.get(pair, 0) + 1
    return counts

stats = get_stats(ids)
top = sorted(stats.items(), key=lambda kv: -kv[1])[:5]
for pair, count in top:
    print(pair, count, "回 →", repr(bytes(pair).decode("utf-8", errors="replace")))
出力
(227, 129) 15275 回 → '�'
(227, 130) 3720 回 → '�'
(227, 128) 2119 回 → '�'
(159, 227) 1456 回 → '��'
(139, 227) 1339 回 → '��'

Pythonの道具箱：get と lambda

counts.get(pair, 0) は「辞書に pair があればその値、なければ0」を返します。初めて見たペアでもエラーにならずに数え始められる、便利な書き方です。
sorted(…, key=lambda kv: -kv[1]) は「各要素 kv の2番目（回数）にマイナスを付けた値で並べ替える」、つまり回数の多い順です。lambda は、その場で使い捨ての小さな関数を作る書き方です。
次の merge 関数で使う while 条件: は、「条件が正しいあいだ、くり返す」ループです。for と違って、何回くり返すかを先に決めずに、位置 i を自分で1つ進めたり2つ進めたりしたいときに使います。フローチャートの「条件つきの戻り矢印」そのものです。

一番多いのは (227, 129) で、1万5千回以上。これはひらがなの多く（「ぁ」〜「み」あたり）に共通する、最初の2バイトです。ひらがなは日本語で一番よく出てくる文字なので、そのバイトの組も一番多いわけです。バイトの切れ端だけでは文字にならないので � と表示されています。4位と5位の (159, 227) や (139, 227) は、「ある文字の最後のバイト」と「次の文字の最初のバイト」の組です。BPEは文字の切れ目を知らないので、こういう組も数えます。

基礎の補足理解のための最小トレース：zip(ids, ids[1:]) で隣接ペアを数える

長さ5の小さな列 ids = [1, 2, 1, 2, 3] で get_stats(ids) がどう動くか、1歩ずつ追いかけましょう。

Python（読むだけ・実行しなくてOK）
ids = [1, 2, 1, 2, 3]
# ids     :  1,  2,  1,  2,  3
# ids[1:] :  2,  1,  2,  3
# zip結果 : (1,2), (2,1), (1,2), (2,3)   ← 長さ5から4個のペアができる
ステップ pair counts.get(pair, 0) 更新後の counts[pair]
1 (1, 2) 0 1
2 (2, 1) 0 1
3 (1, 2) 1 2 ← 最頻ペア！
4 (2, 3) 0 1

元のリストが長さ nnn のとき、隣接ペアは必ず n−1n - 1n−1 個になります（長さ0や1なら0個で空辞書 {}）。

ステップ2：合体させる

Python（Colabのセルに貼って実行）
def merge(ids, pair, new_id):
    out = []
    i = 0
    while i < len(ids):
        if i < len(ids) - 1 and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id)     # ペアを見つけたら、新しいIDに置き換えて2つ進む
            i += 2
        else:
            out.append(ids[i])
            i += 1
    return out

print(merge([5, 6, 6, 7, 9, 6, 7], (6, 7), 99))
出力
[5, 6, 99, 9, 99]

(6, 7) が2か所とも 99 に置き換わりました。

基礎の補足理解のための最小トレース：merge(ids, pair, new_id) の動きと「連続重複」の落とし穴

merge が for ではなく while を使う理由は、ペアが見つかったときに 2歩進む（i += 2）、見つからないときは 1歩進む（i += 1） と歩幅を切り替えたいからです。

特に注意したいのが、同じIDが3回連続する [5, 5, 5] に (5, 5) -> 99 を適用するケースです。

位置 i 見ている値 (5, 5) と一致？ out に追加 次の i
i = 0 ids[0]=5, ids[1]=5 はい 99 0 + 2 = 2
i = 2 ids[2]=5（末尾なので i < len(ids) - 1 は偽） いいえ 5 2 + 1 = 3（終了）

結果は [99, 5] になります。左から貪欲に2個ずつ消費していくため、3個目の 5 はそのまま残ります。また、if i < len(ids) - 1 and ... を左側に書くことで、末尾要素のときに ids[i + 1] を読んで IndexError になるのを防いでいます。

ステップ3：くり返して学習する

0〜255はバイトそのものに使っているので、新しいトークンは256番から番号をつけていきます。300回合体させて、語彙556個のトークナイザーを作りましょう。

Python（Colabのセルに貼って実行）
num_merges = 300
merges = {}                     # (a, b) → 新しいID（合体ルール）
vocab = {i: bytes([i]) for i in range(256)}   # ID → バイト列
work = list(ids)
for k in range(num_merges):
    stats = get_stats(work)
    pair = max(stats, key=stats.get)            # いちばん多いペア
    new_id = 256 + k
    work = merge(work, pair, new_id)
    merges[pair] = new_id
    vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]

print("学習前：", len(ids), "トークン → 学習後：", len(work), "トークン")
print("圧縮率：", round(len(ids) / len(work), 2), "倍")
出力
学習前： 89160 トークン → 学習後： 28975 トークン
圧縮率： 3.08 倍

max(stats, key=stats.get) は「回数が最大のペア」を選ぶ書き方です。CPUで1〜2分かかります。300回の合体で、約9万バイトが約2万9千トークンに、3分の1ほどに縮みました。1トークンに平均3バイト、つまり日本語なら平均1文字ほどです。どんなトークンができたか、のぞいてみましょう。

Python（Colabのセルに貼って実行）
learned = [vocab[256 + k].decode("utf-8", errors="replace") for k in range(num_merges)]
print("最初の30個：", learned[:30])
print("最後の30個：", learned[-30:])
出力
最初の30個： ['�', '�', '�', 'の', 'た', 'い', '。', 'に', 'っ', 'は', 'な', 'て', 'し', 'か', 'で', 'た。', 'と', 'を', '、', 'る', 'う', '�', '私', 'が', 'ら', 'も', 'そ', 'れ', '�', '�']
最後の30個： ['」とい', '�', '会', '意', 'か」\n「', 'より', '知', '�', '私には', '始', 'そこ', '��', '二人', '向', 'ありません', '掛', '来た', '変', '好', '手', 'の上', 'るの', '付', '��', '外', '自分', '�', '��え', '��', '然']

最初のうちは、バイトの組み合わせから「の」「た」「い」などのひらがな1文字や、「私」のようなよく出る漢字が作られていきます。後半になると、「ありません」「私には」「自分」「二人」「来た」のようなよく出る言葉や言い回しがまるごと1トークンになっています。「」とい」「か」\n「」のように、会話のかぎかっこの切れ目をまたいだトークンもできていますね。誰も日本語の文法を教えていないのに、「よく出る組を合体させる」だけで、言葉らしい単位が浮かび上がってきました。

ところどころに残っている � は、文字の途中までのバイトを合体させたトークンです。たとえば、ある漢字の最初の2バイトは、その漢字の仲間（同じ部首の漢字など）に共通することがあるので、それだけで合体してしまうのです。

エンコードとデコード

学習した合体ルールを使って、新しい文章をトークンに変える（エンコード）関数と、元に戻す（デコード）関数を作ります。

Python（Colabのセルに貼って実行）
def decode(token_ids):
    return b"".join(vocab[t] for t in token_ids).decode("utf-8", errors="replace")

def encode(s):
    ids = list(s.encode("utf-8"))
    while len(ids) >= 2:
        stats = get_stats(ids)
        # 学習で「先に」覚えたルール（番号が小さいもの）から順に使う
        pair = min(stats, key=lambda p: merges.get(p, float("inf")))
        if pair not in merges:
            break                       # もう使えるルールがない
        ids = merge(ids, pair, merges[pair])
    return ids

sample = "先生は奥さんと話をしていた。"
tokens = encode(sample)
print(len(sample.encode("utf-8")), "バイト →", len(tokens), "トークン")
print([decode([t]) for t in tokens])
print(decode(tokens) == sample)
出力
42 バイト → 8 トークン
['先生は', '奥さん', 'と', '�', '��', 'を', 'して', 'いた。']
True

42バイトが8トークンになりました。「先生は」「奥さん」「いた。」がまるごと1トークンです。一方、「話」は学習に使った最初の3万字にあまり出てこなかったので、� と �� の2つのバイトの切れ端に分かれています（3バイトが1＋2に分かれた）。それでも最後の行の True のとおり、つなげて読めば元の文章に完全に戻ります。第2章の「鰯」と同じことが、自分のトークナイザーで起きたわけです。

理論の小部屋：エンコードは「学習した順番」でルールを使う

エンコードでは、文章をバイトに分解したあと、学習したときと同じ順番で合体ルールを適用します。「先に覚えたルール（番号が小さい）」が、学習データでよく出てきた組だからです。順番を変えると、学習時とは違う区切り方になってしまいます。

デコードはもっと簡単で、各トークンのバイト列をつなげて、UTF-8として読むだけです。errors="replace" は「途中で切れたバイトがあっても、エラーにせず � にする」指定です。LLMが生成の途中でバイトの途中までしか出していない瞬間があるので、これが必要になります。

基礎の補足なぜ「学習した順番（最小ID優先）」が必須なのか？具体例で確かめる

学習で次の順番に3つのルールを覚えたとします（番号が小さいほど先に学習したルール）。

  1. (1, 2) → 256（1番目に学習）
  2. (256, 3) → 257（2番目に学習：256 が作られて初めて使える！）
  3. (2, 3) → 258（3番目に学習）

ここで入力 [1, 2, 3] をエンコードしてみましょう。

Python（読むだけ・実行しなくてOK）
# 正しい手順：学習順（番号が小さいルールから）適用する
# [1, 2, 3] → (1,2)が256、(2,3)が258 → 小さい256を先に適用 → [256, 3]
# [256, 3]  → (256,3)が257 → 適用 → [257]   ← 学習時と同じ1トークン！

# 誤った手順：順番を無視して (2, 3) → 258 を先に適用してしまう
# [1, 2, 3] → [1, 258]   ← もう (256, 3) を作れない！ 学習時と違う2トークンに分裂！

だから encode では、min(stats, key=lambda p: merges.get(p, float("inf"))) と書いて、いま並んでいるペアのうち、ルール番号がもっとも小さいもの（＝いちばん先に学習したルール）を毎回1つ選んで合体します。ルールに載っていないペアには float("inf")（無限大）を返すので、使えるルールが1つでもあれば必ずそちらが選ばれます。

本格版：Hugging Faceの tokenizers

自作版は仕組みを学ぶのに最適ですが、遅すぎて本物のデータには使えません。実務では、高速に書かれたライブラリを使います。Hugging Faceの tokenizers は、内部がRustという言語で書かれていて、自作版の何百倍も速く動きます。『こころ』全体で、語彙4000のバイトレベルBPEを学習させてみましょう。

Python（Colabのセルに貼って実行）
from tokenizers import Tokenizer, models, trainers, pre_tokenizers, decoders

bpe = Tokenizer(models.BPE())
bpe.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
bpe.decoder = decoders.ByteLevel()
trainer = trainers.BpeTrainer(vocab_size=4000, initial_alphabet=pre_tokenizers.ByteLevel.alphabet())
bpe.train_from_iterator(text.split("\n"), trainer=trainer)

enc = bpe.encode("先生は奥さんと話をしていた。")
print(enc.ids)
print([bpe.decode([i]) for i in enc.ids])
出力
[485, 1636, 1891, 685, 264]
['先生は', '奥さんと', '話を', 'していた', '。']

一瞬で終わりました。『こころ』全体で学習し、語彙も大きいので、「奥さんと」「話を」「していた」がそれぞれ1トークン。文全体がたった5トークンです。

理論の小部屋：語彙サイズのトレードオフ（サブワードの絶妙なバランス）

BPEのようなサブワード（単語の断片）トークナイザーは、「文字単位」と「単語単位」のいいとこ取りをした架け橋です。

  • 文字単位（第13章まで）：語彙数は数千文字でコンパクトですが、文章のトークン列がとても長くなります。Attentionの計算量は列の長さの2乗（T×TT \times TT×T）で増えるため、文章が長いと計算が急激に重くなります。
  • 単語単位：文章のトークン列は短くなりますが、日本語や英語のすべての単語を網羅しようとすると語彙数が数十万〜数百万に爆発し、辞書にない未知語（新語や誤字）を扱えなくなります。
  • サブワード（BPE）：よく出る単語や言い回しは1トークンにまとめ、珍しい単語は細かい断片（最後は1バイト単位）に分解して表します。未知語を一切出さずに、列の長さを適度に短く抑えられます。

語彙サイズ（合体回数）をどれくらいにするかはトレードオフです。

  • 👍 語彙を大きくすると、同じ文章が少ないトークンで表せる（列が短くなり、計算が軽く、遠くまで見渡せる）
  • 👎 語彙を大きくしすぎると、埋め込みと出力層のパラメータ（語彙数 ×\times× 幅）が膨らみ、めったに出てこないトークンの学習が追いつかなくなる

実際のLLMの語彙サイズは、GPT-2が約5万、Qwen2.5が約15万、多言語のモデルほど大きい傾向です。日本語・中国語・英語……と多くの言語の「よく出る組」を入れるには、大きな辞書が必要だからです。

基礎の補足数字で見る語彙サイズのトレードオフ（V×dV \times dV×d vs T2T^2T2）

埋め込み幅 d=768d = 768d=768 のモデルで、語彙サイズ VVV を変えたときの重みと計算量のバランスを比べてみましょう。

語彙サイズ VVV 埋め込み表 wte のパラメータ数（V×768V \times 768V×768） 同じ日本語文章のトークン数 TTT（目安） Attentionのスコア表サイズ（T2T^2T2）
256（バイトそのまま） 約20万個（極小） 約3,000（長い） 900万マス（重い）
2,000（小型BPE） 約154万個 約650 42万マス
50,000（GPT-2級） 約3,840万個 約400 16万マス
150,000（多言語LLM級） 約1.15億個（巨大） 約300（短い） 9万マス（軽い）

語彙を増やすほど TTT が短くなって T2T^2T2 のAttentionが激減する一方、埋め込み層と出力層のサイズ V×dV \times dV×d が直線的に膨らみます。そのため、モデルの大きさや対応言語数に合わせてちょうど良い VVV を選びます。

Python（Colabのセルに貼って実行）
def get_batch(data, batch_size, T, g):
    ix = torch.randint(0, len(data) - T, (batch_size,), generator=g)
    return (torch.stack([data[i:i + T] for i in ix]),
            torch.stack([data[i + 1:i + T + 1] for i in ix]))

@torch.no_grad()
def val_loss_per_token(model, data, T):
    model.eval()
    starts = range(0, len(data) - T - 1, T)
    xs = torch.stack([data[i:i + T] for i in starts])
    ys = torch.stack([data[i + 1:i + T + 1] for i in starts])
    loss = model(xs, ys)[1].item()
    model.train()
    return loss

torch.manual_seed(0)
g = torch.Generator().manual_seed(0)
model = GPT(bpe.get_vocab_size(), block_size=64, n_embd=64, n_head=4, n_layer=2, dropout=0.1)
opt = torch.optim.AdamW(model.parameters(), lr=3e-3)
for step in range(1501):
    x, y = get_batch(train_ids, 32, 64, g)
    _, loss = model(x, y)
    opt.zero_grad()
    loss.backward()
    opt.step()
    if step % 500 == 0:
        vl = val_loss_per_token(model, val_ids, 64)
        print(f"ステップ {step:4d}：検証（1トークンあたり）{vl:.3f}")

ミナト

4.98……？ 第12章の文字版は3.10だったのに、ずっと悪くなってませんか？

ボンゴ先生

ここが大事な落とし穴だ！ 文字版の損失は「1文字あたりの驚き」、BPE版は「1トークンあたりの驚き」。1トークンには平均1.5文字入っているから、1トークンを当てるのは、1.5文字ぶんをまとめて当てるのと同じくらい難しい。単位が違うものを比べてはいけない。メートルとインチを比べるようなものだ。

理論の小部屋：1文字あたりの損失に直して比べる

トークナイザーが違うモデルを比べるときは、文章全体の驚きの合計を、文字数（またはバイト数）で割って比べます。

1文字あたりの損失=1トークンあたりの損失×トークン数文字数\text{1文字あたりの損失} = \frac{\text{1トークンあたりの損失} \times \text{トークン数}}{\text{文字数}}1文字あたりの損失=文字数1トークンあたりの損失×トークン数​

小さな数字で手計算：たとえば検証データが 10,000文字 で、BPEでは 4,000トークン（1トークンあたり平均2.5文字）になったとします。このとき1トークンあたりの損失が 3.0 なら、文章全体の総損失は 3.0×4,000=12,0003.0 \times 4{,}000 = 12{,}0003.0×4,000=12,000。これを文字数 10,00010{,}00010,000 で割ると、1文字あたり 12,000÷10,000=1.212{,}000 \div 10{,}000 = 1.212,000÷10,000=1.2 になります。

Python（Colabのセルに貼って実行）
per_token = val_loss_per_token(model, val_ids, 64)
per_char = per_token * len(val_ids) / len(text[n:])
print(f"1トークンあたり {per_token:.3f} → 1文字あたり {per_char:.3f}")
出力
1トークンあたり 4.976 → 1文字あたり 3.225

1文字あたりに直すと 約3.23。第12章の文字版（同じ大きさのモデル・同じステップ数で 3.10）と比べると、BPE版のほうが少し悪い、という結果になりました。

あれ？ 本物のLLMはみんなBPEなのに、文字版に負けちゃうんですか？

理論の小部屋：BPEの利点が出るのは、データが多いとき

BPEにすると、語彙が2061文字から2000トークンに変わるだけでなく、1つ1つのトークンが出てくる回数が減ります。「話を」というトークンは、「話」という文字よりずっと出てくる回数が少ないですよね。『こころ』の14万字では、それぞれのトークンをしっかり学ぶには例が足りず、丸暗記（過学習）しやすくなるのです。

一方、データが何億・何兆トークンもあれば、どのトークンも十分に学べるので、「同じ窓で遠くまで見渡せる」「言い回しを1つの部品として扱える」というBPEの利点が勝ちます。本物のLLMがみなBPEのようなトークナイザーを使うのは、そのためです。手法の良し悪しは、データの大きさとセットで考える。これも大事な教訓です。

つまずき注意：比較の注意

ただし、この比較には少しだけ「ずる」があります。BPEのトークナイザーは『こころ』全体（検証データの部分も含む）で学習させたので、検証データによく出る言い回しを知っています。厳密な実験では、トークナイザーも訓練データだけで作るべきです。研究で数字を比べるときは、こういうデータの漏れ（leakage）に気をつけましょう（第20章で詳しく）。

もっと深く日本語のトークナイズと、ほかの方式
  • 事前分割：GPT-2などは、BPEの前に正規表現で「単語・数字・記号」に分けておき、単語をまたぐ合体を禁止しています（第2章の ' am' のように空白が単語の前にくっつくのはこのため）。日本語は単語の間に空白がないので、この分割があまり効きません。
  • 形態素解析：日本語では昔から、MeCabなどの辞書を使って単語（形態素）に分ける方法がよく使われてきました。日本語特化のLLMの中には、形態素解析とBPEを組み合わせるものもあります。
  • SentencePiece / Unigram：BPEとは逆に、大きな語彙から始めて「消しても困らないトークン」を削っていく方式（Unigram言語モデル）もあります。Googleの SentencePiece というライブラリが有名で、多くの多言語モデルが使っています。
  • Unicode正規化：「Ａ」（全角）と「A」（半角）、「ｶ」と「カ」のように、見た目が同じでも文字コードが違う文字があります。unicodedata.normalize("NFKC", text) で統一してからトークナイズすると、語彙の無駄が減ります。
